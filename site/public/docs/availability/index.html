Explanation

Kubernetes availability and failure scope

“High availability” is a behavior under a named failure. State which behavior should continue, where the failed component lives, and how recovery works.

Verified local Host Agent test · 2026-09-25. Three fresh Incus system container server guests were provisioned and configured through typed Host Agent MCP operations as a K3s v1.31.8+k3s1 cluster with embedded-etcd. The guests shared one physical host. With one guest stopped, 2 of 3 nodes were Ready; a typed ConfigMap apply and read both succeeded through the surviving control plane. Starting the guest restored 3 of 3 Ready nodes.

The test used K3s provider 1.0.2. The Host Agent process reported runtime dev and catalog revision sha256:1399404a31f51c6120e4ea84c5691b61e93a5c4fb23356600bfd28b3aa6f9e2b. The published @opute/host-agent@0.2.2 canary separately proves the authenticated read-only first-success path; it did not test this HA setup flow.

This result covers one Incus guest/server failure on one physical host. It does not establish host or site failure recovery, network partition behavior, workload serving, durable application data, new workload scheduling, or external endpoint failover. The membership probe also reported that no external HA endpoint was configured.

Separate the outcomes

One healthy member list is not an availability test. Check each property that matters to the user:

  • Control-plane writes: can the Kubernetes API accept a change while a server is down?
  • Existing workloads: do already-running Pods continue on a surviving node?
  • New scheduling: can the control plane place or replace workloads?
  • Application serving: does the user-facing endpoint remain reachable?
  • Durable state: does application data remain readable and writable?

Record these separately. A service returning HTTP 200 does not prove Kubernetes write availability, and a healthy cluster status does not prove the application path is serving.

In this K3s provider, get-cluster-info.readyNodeCount and each node's status expose the per-node observation. Its aggregate ready field is true when at least one node is Ready; that boolean alone does not prove etcd quorum or application health. The typed write and read during the guest failure supply the API write-continuity evidence for this specific test.

K3s datastore quorum

For embedded etcd, K3s documents an HA cluster as three or more server nodes. Quorum requires a majority. With only two voting members, losing either member removes quorum, so automatic Kubernetes write continuity is not established.

With an external datastore, K3s uses two or more server nodes. The external datastore has its own availability requirements and must survive the failure being tested; two K3s servers alone do not make that database highly available.

  • K3s: High Availability Embedded etcd
  • K3s: High Availability External DB

Failure domains matter

Three guests on one physical computer can demonstrate guest-level setup and failure behavior. They share the computer’s power, storage, host networking, and physical failure domain, so that test cannot establish resilience to losing the host or site. State the tested boundary with the result.

What remains untested

  • physical-host or site failure
  • network partition
  • application workload continued serving
  • durable application data survived
  • new workload scheduling during failure
  • external endpoint failover
  • the published npm package HA setup path

What a clean setup test should record

  1. Start from isolated hosts with no K3s service, datastore, or prior cluster membership. If the claim includes installing and enrolling Host Agent itself, test that bootstrap as a separate step.
  2. Record each exact Host Agent identity, software revision, active provider/catalog revision, and the empty baseline.
  3. Use the exact setup capabilities exposed by the tested release. Platform may coordinate authorized cross-host intent and durable runs; each host change should remain attributable to its owning Host Agent. If any setup step uses a shell, CLI, cloud console, or other out-of-band path, record it and narrow the claim: that run did not prove Host Agent-only setup.
  4. Verify the expected server membership and the configured datastore mode before injecting failure.
  5. Stop or isolate each server in turn. Measure API reads and writes, workload serving, durable application state, and recovery separately.
  6. Restore the failed node through the supported typed path, verify it rejoins, and retain redacted run evidence.

A successful join proves membership, not clean-room bootstrap or availability. Only the failure checks prove the stated behavior. Use disposable, isolated test hosts for destructive setup and failure injection.

Opute ownership boundary

Host Agent is the typed executor on one host. Opute Platform owns intent, authorization, routing, and durable orchestration across hosts. A multi-host result must show both the coordinator’s durable outcome and the Host Agent evidence for each affected host. See how the products fit together and how recipes and plans work.

This guide states the evidence required for an HA claim. Check the release reference and live tools/list for the capabilities available in a particular installation.
